# README 中展示 GIF 与 MOV

## 1. 当前状态

现在有三张说明配图：`overview.png`、`workflow.png`、`naming.png`。它们解释工具规则，**不是用实际表情生成的前后对比**。真实演示素材尚未提供，没有虚构或替代用户选择的真实素材。

## 2. 发布前的素材确认

- 确认角色/动画/MOV/GIF的权利或公开展示及下载许可。
- 公开仓库中的原片可以被下载，删除提交也不一定能清除已下载的副本。
- 核查 MOV 元数据、文件名、水印、画面与声音是否泄露不希望公开的信息；去除隐私前先保存本地备份，不自动覆写原件。
- 在每组示例的 `ATTRIBUTION.md` 写明来源、作者、许可或授权范围。未确定时不要自动套用代码许可证。
- 别把待处理的私人素材放入 Git 跟踪目录；可在被忽略的 `private/` 中检查，再只复制获许可的文件。

## 3. GIF 直接嵌入

获得真实媒体并创建对应文件后，才把以下示例加入主 README（路径仅为示例，目前文件不存在）：

```markdown
![比心：220×220 透明白描边循环 GIF](examples/heart/220gif/比心.gif)
```

并列展示可用 Markdown 表格，不要为了排版改变原始 GIF 文件的像素尺寸：

```markdown
| 120×120 | 220×220 | 330×330 |
| --- | --- | --- |
| ![120px](examples/heart/120gif/比心.gif) | ![220px](examples/heart/220gif/比心.gif) | ![330px](examples/heart/330gif/比心.gif) |
```

建议另做白/灰/深底的**静态检查图**，清楚标注它是合成预览，真正成品 GIF 仍保持原透明规则。不要把棋盘格永久铺进透明成品后还称为透明文件。

## 4. MOV 用封面 + 原文件链接

GitHub README 的 HTML 会被清理，不应依赖自己写的 `<video>` 标签。MOV 是容器，实际编码与播放器支持也会影响播放。可靠的降级展示：

```markdown
[![点击查看 MOV 原片](examples/heart/source-cover.png)](examples/heart/source.mov)

[查看或下载 MOV 原片](examples/heart/source.mov)
```

从已经确认可公开的源片提取一帧封面（在干净目录运行；实际文件路径请替换）：

```bash
ffmpeg -n -ss 0.5 -i "/实际路径/已获许可的原片.mov" \
  -frames:v 1 "/实际路径/source-cover.png"
```

`-n` 防止覆盖已有封面。选择能体现动作的画面，避免取到首尾空帧。若原片太短，应调整时间点。

如果确实需要 GitHub 内嵌视频，可在支持媒体上传的 GitHub 编辑/评论入口上传合适的视频并使用平台生成的附件链接，再在 GitHub 实际预览验证。不要伪造附件 URL，也不要把普通仓库 `.mov` 链接当成必然内嵌的播放器。为兼容播放可以额外提供 H.264 MP4 预览，但不应替换或篡改标为 MOV 的原文件。

## 5. 控制仓库体积

- GIF 仅保留少量代表性示例；别将所有批次或调试帧都提交。
- 小型原片可放 `examples/`；较大的媒体可作为 Release 附件，或按需求使用 Git LFS。
- GitHub 网页上传和普通 Git 单文件限制不同，且可能随平台政策变化；以当前官方限制为准，不等失败后才拆文件。
- 如用 Git LFS，先核对其带宽/配额及 README 展示效果；并保留清晰的原片下载入口。

## 6. 推荐最终展示

1. 一组黑底原片封面 → 一张 220px 成品 GIF 动画；
2. 三尺寸成品并排对比；
3. 一张白/灰/深底边缘检查图；
4. 可选一组经确认保留装饰背景的对照，明确“原画面不透明”；
5. 每组原片下载链接、背景分支、实际尺寸及素材授权说明。
